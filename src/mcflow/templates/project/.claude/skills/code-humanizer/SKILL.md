# Code humanizer

First draft (Stage 3). The final version, with tests that prove behaviour is unchanged, arrives in Stage 5.

## Ground rules

- **Behaviour doesn't change.** Run the project's tests before and after, and re-run the in-game checks if anything at runtime could differ. If a change could alter behaviour, it isn't a humanizer change: leave it, or raise it as a bug.
- **Follow the project's own conventions** (naming, brace style, import order, comment voice) rather than personal taste.
- **Never touch generated files** (anything marked "Generated by…"). Change the generator instead, if at all.
- Keep the diff small and explain each kind of change in one line.

## What to remove or fix

1. **Comments that restate the code** (`// increment i`, a Javadoc that repeats the method name). Keep comments that say *why*: version quirks, workarounds, measured facts, constraints.
2. **Dead code and scaffolding:** unused methods, fields and imports; debug flags; "spike"/"TODO: remove" leftovers; parameters nothing reads.
3. **Duplicate paths:** two handlers or helpers that do the same job. Keep the one that covers every case, and say in a comment why the other isn't needed.
4. **Defensive checks for impossible states:** null checks on values that can't be null, `Math.max(x, 0)` hiding an initialisation-order bug (fix the order instead), work the framework already does (Bukkit cancels a plugin's tasks on disable).
5. **Generic names** (`data`, `result`, `handle`, `doStuff`, `temp`) where a specific one is obvious.
6. **Inconsistent style** within a file: mixed naming, mixed early-return style, stray blank lines.

## What to leave alone

- Defensive code at trust boundaries: player input, network packets, reflection into server internals, files on disk.
- Comments that cite a version, a measured value or a source.
- Short names in tight, conventional scopes (`i`, `p` for a player in a handler, `e` for an entry).

## Output

The edited files, the before/after test results, and a short list of what changed and why.
