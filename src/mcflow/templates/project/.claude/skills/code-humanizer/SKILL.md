# Code humanizer

A cleanup that changes behaviour is a bug. Every run is bracketed by a snapshot and a check, and a failed check means you revert the change that caused it.

## 1. Snapshot first

```
mcflow humanize snapshot <project>
```

It builds the plugin, runs its tests, and records which tests pass and the public API (every public class, method and field, read from the compiled classes with `javap`). If the build fails, fix that first: there's nothing to compare against.

## 2. Clean up only this task's code

Work on the files and lines this task changed (`git diff`), not the whole project. Follow the project's own conventions (naming, braces, import order, comment voice) rather than personal taste. Never edit generated files (marked "Generated by…"); change the generator if anything.

Remove or fix:

1. **Comments that restate the code** (`// increment i`, a Javadoc that repeats the method name). Keep comments that say *why*: version quirks, workarounds, measured facts, links to research or knowledge entries.
2. **Dead code and scaffolding:** unused methods, fields, imports and parameters; debug flags and logging left from development; "spike" or "TODO: remove" leftovers.
3. **Duplicate paths:** two handlers or helpers doing the same job. Keep the one that covers every case, and say in a comment why the other isn't needed if it's not obvious.
4. **Defensive checks for impossible states:** null checks on values that can't be null; `Math.max(x, 0)` hiding an initialisation-order bug (fix the order instead); cleanup the framework already does (Bukkit cancels a plugin's tasks and unregisters its listeners on disable).
5. **Generic names** (`data`, `result`, `handle`, `temp`, `doStuff`) where a specific one is obvious.
6. **Clever code a reader must decode:** a non-short-circuit `|` used on purpose, nested ternaries, side effects inside conditions. Make the intent explicit.
7. **Inconsistent style** within a file.

Leave alone:

- Defensive code at trust boundaries: player input, network packets, reflection into server internals, files and configs on disk.
- Comments that cite a version, a measured value or a source.
- Short names in tight, conventional scopes (`i`, `p` for a player in a handler, `e` for an entry).
- **Public API.** Renaming a public method or event handler breaks callers (and the check). If a public name is truly wrong, raise it with the user as its own change.

## 3. Check

```
mcflow humanize check <project>
```

It rebuilds, reruns the tests and compares with the snapshot. It fails if a test that passed now fails, a test disappeared, or any public signature changed. **On a failure, revert the edit that caused it**; don't adjust tests to fit.

The check can't prove two programs equivalent: it catches what tests pin and what the API exposes. For behaviour no test covers, the re-verify step (pipeline step 6: build, tests, a quick in-game check) is the second line.

## 4. Report

List what changed, by kind (for example "removed 2 unused methods, 1 duplicate listener, 3 restating comments"), and the check's result.
